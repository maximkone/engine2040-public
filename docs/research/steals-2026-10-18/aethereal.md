One value, one encoding: a canonical byte layout with a decode budget | iamacoffeepot/aethereal@main:docs/adr/0002-the-byte-layout-of-plain-data.md:14,16-31,33-37,39-49,53-57 and crates/aethereal-data/src/budget.rs:7-9,25-34 (read 2026-10-18) | MIT OR Apache-2.0 | SIM (wire and snapshot) | lands crates/net/src/delta.rs and crates/save | M
   Idea: a value is encoded by its shape alone -- no type names, no field tags, no version in the bytes. Widths are fixed little-endian; counts and variant selectors are u32 little-endian; a map's pairs are written in ascending key order and no key appears twice, with the key order stated per key shape (integers by value, strings by UTF-8 bytes with prefix first). Three rules make "one value, one encoding" hold: integers are fixed width (no varint), map pairs are sorted, and a float is written bit for bit (two NaNs with different bits are different bytes). A decoder refuses a boolean or option byte other than 0/1, non-UTF-8 text, a selector that names no variant, input that ends early, and input with bytes left over. And a count is not trusted: `Budget { remaining }` is charged per allocation and refuses past the end (`BudgetExceeded { requested, remaining }`), so a hostile count cannot make the decoder allocate.
   Maps: our hash law says the same complete input fixture gives the same hash, and our net codec already writes bytes that are compared. The transferable parts are (a) the map-key ordering rule stated once so two writers agree, (b) the bit-for-bit float rule (we already hash LE bytes; this states it as a wire rule), and (c) the decode budget -- our snapshot decode reads a count from the wire, and a budget makes a corrupt or hostile count a typed refusal instead of a big allocation.
   Moves: a decode that trusts a length -> a decode that charges a budget and refuses; key order becomes a checked rule (out-of-order or duplicate keys are refused) rather than a convention.
   Proof: cargo test -p engine-net --lib canonical x2 (two encoders of the same value give byte-equal output regardless of map insertion order; a duplicate key, an out-of-order key, a leftover byte and a bad option byte each refuse with a named error; a 4-byte budget with a 1 MB declared count refuses and allocates nothing) plus golden d57b5c8ae3096614 unchanged.
   Risk: fixed-width integers cost bytes on the wire. Kill: if a sorted, fixed-width encoding costs more than 10% kbps on the MP9 corpus, apply the rules to the hash path only and keep the varint wire (tools/mp6-check.mjs decides).

A layout hash over the schema tree, not a hand-bumped version | iamacoffeepot/aethereal@main:crates/aethereal-data/src/kind/layout.rs:6-18,43-58 and docs/adr/0006-kind-identity.md:16-31 (read 2026-10-18) | MIT OR Apache-2.0 | SIM (identity) | lands crates/scene content version and crates/core/src/hash.rs | S
   Idea: a kind is a described type with a name (`Kind { const NAME: KindName }`, names like "aether.audio.note_on"), and a name must conform to a stated grammar so a name that arrives as bytes can be checked. The id that travels is a layout hash: each shape folds a tag byte plus its children's hashes through the one FNV-1a fold (`Shape::Integer(kind)` folds INTEGER then the width code; `Shape::Map { key, value }` folds MAP then both child hashes), so two types share an id only if their shapes match, and a shape change moves the id with no one remembering to bump anything.
   Maps: we already have the fold (core/src/hash.rs). What we hand-bump today is content versioning (crates/scene). Hashing the shape of a record means a field reorder or a width change moves the id by itself, and a name grammar means a bad name from a file is refused at decode.
   Moves: content version 1 hand-bumped -> a hash of the record's shape; an id can be recomputed and compared instead of trusted.
   Proof: cargo test -p engine-scene --lib layout_hash x2 (a field reorder moves the hash; the same shape gives the same hash across two builds and two insertion orders; a non-conforming name refuses) plus golden unchanged.
   Risk: a layout hash changes whenever a field is added, which invalidates saved content. Kill: if a shape hash invalidates more than the single record it describes, keep it as a diagnostic beside a hand-bumped version rather than a replacement.

3. A turn takes one piece of mail and returns effects | iamacoffeepot/aethereal@main:docs/adr/0009-an-actors-turn.md:18-49 (read 2026-10-18) | MIT OR Apache-2.0 | SIM (boundary) | lands crates/ai (embedded seam) and crates/rules | S
   Idea: an actor's life has three parts -- `begin` (make it from a config, running inside the parent's turn), a `handle` per item, and `end` (its closing turn, once, whichever way it closed). A turn takes ONE item and returns effects; it does not act as it runs. The ADR lists the three costs of acting immediately: each call site needs its own answer for what happens to a thing in flight, a handler that fails halfway has already sent mail, and a guest pays per crossing. `Fault { kind: KindId, bytes }` is why a turn could not go on, and it carries a kind so the reason is data, not a string.
   Maps: our AI seam already runs brief -> patch -> run and our rules script emits actions the arena applies (rules/src/lib.rs:1-8). The reusable idea is that a handler returns effects instead of performing them, so a failure mid-handler leaves nothing half-sent, and the failure reason is a typed kind plus bytes -- which is exactly what a typed, no-strings seam (crates/ai) wants.
   Moves: an action applied inside the handler -> effects returned and applied by the tick; a failure reason from a string -> a kind + bytes. Unmeasured.
   Proof: cargo test -p engine-ai --lib turn x2 (a handler that fails after proposing two effects applies zero; the fault carries a kind; the same inputs give the same applied-effect list) plus golden unchanged.
   Risk: collecting effects allocates per turn. Kill: if the effect list allocates inside the tick (violates the per-tick allocation rule), keep the fixed-capacity apply path and only take the typed Fault.
