## What it is

A turn-based, grid-based roguelike engine in small crates, with the algorithmic core free of Bevy so map generation, pathfinding and rules run headless and build for wasm. The interesting parts are all integer, allocation-conscious and documented with the invariant they keep.

## Steals

**1. Symmetric shadowcasting into a caller-owned buffer, recomputed without allocating** | `crates/rl-grid/src/fov.rs:9-10` ("Output goes into a `BitGrid` the caller owns and reuses, so a viewshed recompute allocates nothing."), `:3-7` ("a floor tile is revealed only when its centre lies inside the arc. That last rule is what makes the result symmetric: if A can see B, B can see A, for any two floor tiles. Walls are revealed more generously so rooms read as solid."), `:21-36` (`compute(source, origin, range, out)`: clear `out`, the origin is always visible, `range <= 0` sees the origin alone, then four quadrants of `scan(Row{depth, start, end})` with rational `Slope{num: i64, den: i64}` bounds), `:38-44` (`can_see` = one full scan then a lookup, with the note that one scan plus many tests beats many scans) | MIT OR Apache-2.0 | SIM (spatial) | lands on `crates/spatial` (`isovist.rs` is the integer-cm visibility *polygon*, `crates/spatial/src/isovist.rs:281`), and on `crates/ai`'s sight-gated chase
Idea: two things to take. One, the symmetry guarantee and the rule that buys it (a tile counts only when its centre is in the arc, so the answer cannot depend on which side asks) plus the test that proves it over a seeded grid. Two, the viewshed is written into a caller-owned buffer, so a per-tick recompute for N observers allocates nothing.
Moves: our visibility is a polygon against wall segments; a tile/lattice sight layer (for hearing, stealth and AI) wants the symmetric answer and the zero-alloc rewrite. Target: `can_see(a, b) == can_see(b, a)` for every open pair in a seeded arena, and 0 allocations over N recomputes.
Kill: kill if the existing ray-cast LOS is already symmetric and proven by that test, or if per-tick recomputes are not in the budget (then only the test is worth taking).

**2. A double-buffered tile field whose step rule is passed in** | `crates/rl-grid/src/field.rs:1-11` ("A rule reads the field as it stood and writes every cell's next value into a second buffer, and the two swap. Nothing a step changes can move again within the same step, so a fire cannot run across a map in one turn, and a cloud spreads the same way whichever order its cells are visited in. The second buffer is kept between steps, so a step allocates nothing."), `:13-22` (doctest: a wave rule advances exactly one cell and asserts `[9, 9, 0, 0, 0]`, "one step, one cell further, however it was visited"), `:26-39` (`TileField<T>{now, next}`, `Default::default()` outside the field), `:35-51` (`new`, `get`, `set`, `update`) | MIT OR Apache-2.0 | SIM (fields) | lands on the fire/gas/sound spread in `crates/physfx` and the hearing layer in `crates/spatial`
Idea: one generic type for every spreading or fading field, with the rule a closure. The two invariants are exactly the ones a hash needs: exactly one cell (or one value step) per tick, and a result independent of visit order. Keeping the second buffer between steps makes the step allocation-free.
Moves: sound spread, fire, gas and smoke become one type with named rules; the doctest is the acceptance test ("one step, one cell further, however it was visited"), and an allocation count over N steps proves the reuse.
Kill: kill if the field is already double-buffered and a visit-order test exists; then only the "rule as a parameter" part is worth taking (so one field type serves every spread).

**3. Dijkstra map: a region-bounded flood, an inverted safety map, and the step rules pinned into the map** | `crates/rl-grid/src/dijkstra.rs:3-9` ("A map holds, for every cell in a region, its cost to the nearest goal. Building it is one search from every goal at once ... fifty monsters share one map instead of running fifty searches. Maps are bounded to a region so a continuous world never floods a million cells per turn. Cells outside the region are unreached."), `:11-14` ("Values are signed so a map can be inverted into a safety map: scale every value by a negative factor and `rescan`, and the low points become the places far from the goals that are also reachable without passing near them. Fleeing monsters descend that."), `:28-50` (`DijkstraMap{region: Rect, values: Vec<i32>, heap, rules: PathRules, ...}`: "The rules the last flood stepped by, so descending takes only the steps it took" and the per-diagonal corner flags, with the bug story that unrecorded corners left "a mover whose cheapest way was that diagonal stood where it was for ever") | MIT OR Apache-2.0 | SIM (nav/AI) | lands on `crates/nav/src/flow.rs:47-118` (`bake_flow` is a 4-dir BFS from one goal with fixed N,S,W,E tie-break in `follow`; one goal = one field, no region bound, no flee map) and `crates/nav`'s bake/validator
Idea: three separable improvements. (a) Bound the flood to the pit (`Rect`) so a bake never touches the whole grid. (b) A safety map is the same field negated and rescanned, so a flee field is nearly free and needs no second algorithm. (c) Pin the step rules *into the map* at bake time — the tie-break and, in an 8-dir grid, the corner flags — so `follow` cannot take a step `bake` did not price; our 4-dir case still wants the tie rule stored rather than re-derived.
Moves: a bake's validator can then assert "every step the follower takes was priced by the bake" (today the two use different orders), and a flee goal costs one negate+rescan.
Kill: kill the 8-dir corner flags if the tile layer stays 4-dir (no diagonals to refuse); keep the region bound and the safety map regardless. Kill all of it if the bake is already bounded and the validator already compares follower steps to bake steps.

**4. Integer-clock turn queue: tie-break by insertion order, id excluded, and Ord/PartialEq written by hand** | `crates/rl-core/src/turn.rs:8-11` ("The clock is an integer in hundredths of a turn. An `f32` clock cannot promise that the same inputs always give the same order once it has accumulated enough additions to lose low bits, and a scheduler is the last place to relax determinism."), `:22-42` (`BASE_ACTION_COST = 100`; `scaled_cost` = `(base*100).div_ceil(speed)` with speed 0 treated as 1; `reschedule_at` saturating, "a wrapped clock puts an actor in the past and silently reorders everyone else, a saturated one stops visibly"), `:44-73` (`Entry{time, insertion_order, id}`, `Ord` on `(time, insertion_order)` only — "The id is deliberately excluded: it carries no scheduling meaning and its bit order is arbitrary" — and a hand-written `PartialEq` over exactly the fields `Ord` compares, "so `a == b` holds exactly when `cmp` says `Equal`, as Rust's ordering contract requires") | MIT OR Apache-2.0 | SIM (act order) | lands on the act-order/energy rules in `crates/rules` and the order of resolution in `crates/arena`/`crates/combat`
Idea: three rules small enough to take separately. (a) Tie-break simultaneous actors by a monotone insertion counter, never by entity id or hash order. (b) A reschedule saturates, so a very late actor stops visibly instead of landing in the past and reordering everyone. (c) If a heap of entries is compared, write `PartialEq` over exactly the fields `Ord` uses, or the heap's contract is quietly broken.
Moves: the order of resolution becomes provable by construction; add the test that a full queue never reorders across a saturating wrap, and one that two actors given the same time resolve in the order they were inserted.
Kill: kill if the arena already keeps a monotone insertion counter for order and a test covers the wrap; then only the `PartialEq`-over-`Ord` rule is left, and it is a comment if the entry type derives both.

## Also worth a note

`crates/rl-bevy/tests/fingerprint.rs:1-10, 30-53`: a seeded run is folded to one number, and the fold deliberately reads *where actors stand* (sorted by row then column, then by health) rather than their entity ids, because Bevy's allocator renumbers on unrelated spawns and "that is not a change to the run". The test's comment states the re-baseline rule ("A change that means to move it re-baselines the number and says so in the changelog"). Same lesson as our hash law, with a second reason to sort before folding.
