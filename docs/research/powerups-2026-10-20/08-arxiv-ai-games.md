# 08 — arXiv: how an AI builds, tests and fixes a game inside an engine (2026-10-20)

Method: every arXiv id below was opened at `arxiv.org/abs/<id>` on 2026-10-20 and the title, the submission line and the abstract were read there. The export API (`export.arxiv.org/api/query`) returned **429** on every try today, so no id was confirmed through the API; the abs page was the source. GitHub repos were opened live through the GitHub API on 2026-10-20: root listing, the named file, and the LICENSE text. Grades: OBSERVED (read the page/file today), DERIVED (reasoned from what I read), UNKNOWN. No paper number in this file is our runtime result.

**Short answer.** The papers that matter for our door all split the work the same way: a *spec* becomes a list of **keypoints**, each keypoint becomes a **state the engine can put the game into**, and a **bounded interaction** then produces a machine verdict. Nobody lets an LLM look at a game and say "it works". The best four are GameGen-Verifier (2605.07442, MIT code) for keypoint-to-state-injection verification, Game-Creation-Agents (2610.16776, Apache-2.0) for contract-then-gate-then-repair production, AgenticSTS (2607.02255) for a bounded memory contract, and GameXpert-Bench (2608.21833) for splitting our task suite into build / fix / optimize tracks. One correction: CraftBench-UE (2609.23142) is already mirrored by HS30, so its value now is its numbers, not its shape. Everything that needs a frontier model (their own scores, their RL post-training, their LLM judges) is marked RESEARCH-ONLY; the shapes that run on a free model are PORT-CANDIDATE.
