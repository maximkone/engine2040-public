# 15 — Layers above and below

Answer, in one paragraph. The engine has a **vertical stack that is written down and machine-checked at crate granularity only**: `docs/ARCHITECTURE.md` §1 draws the seven levels and `tools/workspace-check.mjs` holds one `allowedEdges` map (lines 19-102) that fails any crate edge that is not on the list, plus a std-only check on `engine-core` (line 822). That map is the real layer rule today (OBSERVED). What is missing is **everything below crate granularity**: there is no rule that a sim crate may not import a presentation crate (`engine-physics` and `engine-arena` both list `engine-anim`, OBSERVED), no rule that the GPU may only be touched under `crates/render/src/present/**` (31 render files outside `present/` name `wgpu::`, OBSERVED), and no rule that a *module* inside a tick crate may not do IO (the only `std::fs` hits in sim crates sit in test modules, OBSERVED). The **horizontal axes are the bigger hole**. Collision layers exist as a 5-row Rust const table (`crates/physics/src/layers.rs`), nav layers exist and are 34 KB of code (`crates/nav/src/layers.rs`, `MESH_VERSION = 2`), the pass report exists (`crates/render/src/pass_report.rs`), the quality knobs exist (`crates/render/src/quality.rs`), the LOD pixel-error pick exists (`crates/render/src/draw.rs`) — and almost none of them is **wired**: `pass_report` has zero callers, `engine_nav::layers` has zero callers outside `nav` (`nav` itself is a door-only leaf: `engine-nav` is used by `engine-endpoint` only, OBSERVED in `docs/CRATE-MAP.md`), `pixel_thresholds_px` is `None` in every constructor, and the input layer stack says "No live consumer yet" in its own source. So the pattern is one line: **the axis data exists; the consumers and the machine checks do not**.


## Rejections

- `uinosoft/zenfg` `crates/zenfg/src/{graph.rs,pass.rs,report.rs}` read live: no "read with no writer" check found in the grepped lines, so ZenFG is a shape donor only, not the validator (Granite is the concrete one).
- `KhronosGroup/glTF` `extensions/2.0/EXT_mesh_lod/README.md` 404s today; the mesh-LOD idea needs another source or none.
- `ros-navigation/navigation2` repo `LICENSE` is mixed SPDX and includes LGPL-2.1-or-later: file-level BSD header read, repo marked risky, ideas only.
- Unity layers / Unreal `ECollisionChannel` / Godot `collision_layer`+`collision_mask`: already mined (LADDER.md) and proprietary → research-only, not re-mined here.
- `bevyengine/bevy` phases/schedules, `jrouwe/Jolt`, `dimforge/rapier`, `meshoptimizer`, `Godot`, `Unreal`, `Unity`, `O3DE`, `Filament`: already mined, skipped.
- `cargo`/`cargo-deny`/`cargo-udeps` for the layer rule: the engine already has its own checker (`tools/workspace-check.mjs` allowlist), no new dependency needed.
- `sokol_gfx` `sg_pass` attachments: pass list is per-attachment, no read/write producer map — weaker than `pass_report.rs`.
- `flecs` "layers" as entity tags: no mask algebra, so it cannot replace `physics::layers`; kept for the system-layer row only.
- `rayon` as a runtime dependency: the engine has its own `JobPool`; adding rayon would break the "one pool, index-ordered merge" rule, so it is a reading donor only.
- `zenfg`/`Granite`/`Dawn`/`Vulkan-Headers` as crate dependencies: all research-only by owner decision D5 — port the idea, write our own code.
