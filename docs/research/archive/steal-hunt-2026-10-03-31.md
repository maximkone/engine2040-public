## CARD 1 — latest-only mailbox video-frame upload (decode thread + channel + take-latest + BGRA swizzle + resize-on-change), external decode only

- Source: `PortalCloudInc/bevy_video@eca2ba442d5f0c718e286cce44a5a5f0c0f69c9d`
  (default-branch HEAD at read) — `src/components.rs` (blob `984fdf4c…`) +
  `src/systems.rs` (blob `f43eed22…`) + `src/plugin.rs` (blob `8c1e3fe1…`)
  + `Cargo.toml` (blob `29e3b5dbe…`) + `LICENSE` (blob `92900a18…`),
  all read live 2026-10-03 via GitHub API.
- License: **MIT** (© 2023 PortalCloudInc, full text read live) — reimplement
  shape only, zero bytes vendored, attribution in the file header.
- What it does — HOW THEY HANDLE it: (a) decode NEVER runs on the frame:
  `VideoDecoder::create` spawns one background thread holding an openh264
  `Decoder`, fed by an mpsc `channel<DecoderMessage::Frame(Vec<u8>)|Stop>`
  (`components.rs`, `add_video_packet`); (b) the thread decodes YUV, converts
  to RGB8 (`write_rgb8` into a fresh `vec![0; w*h*3]`), and publishes through
  `Arc<Mutex<Option<VideoFrame>>>` with `replace` — a latest-only mailbox,
  intermediate frames are dropped, never queued; (c) the frame thread only
  runs `apply_decode` (`systems.rs`, wired as one `Update` system in
  `plugin.rs`): `take_frame_rgb8` (take = empty after read), resize the
  `Image` render target ONLY when dims change (`Extent3d` compare), then
  swizzle RGB→BGRA + opaque alpha (`[src[2], src[1], src[0], 255]`) into the
  `Bgra8UnormSrgb` texture (`COPY_DST|TEXTURE_BINDING|RENDER_ATTACHMENT`);
  (d) teardown is a message (`Drop` sends `Stop`); a gone `Image` removes the
  `VideoDecoder` component instead of crashing. What they cut: no queue
  depth, no YUV-direct upload (TODO in file: "Don't convert YUV -> RGB ->
  BGRA"), no in-tick decode, no audio (packets in, texture out).
- Counterevidence (why NOT their Cargo): `Cargo.toml` deps `openh264 0.4` —
  an encoder-crate dependency our verdict DROPS (RESEARCH-VERDICT:331, GM3
  clean machine). The take is the THREAD + MAILBOX + SWIZZLE shape with
  decode supplied EXTERNALLY (ffmpeg CLI/pipe or OS decoder), never the
  `openh264` crate as a dep.
- Home (existing files): theater/video-texture upload hunks beside
  `crates/game/src/capture.rs` SHOW1-cap (frames out) + a new
  presentation-only upload path feeding the MP7 theater / kill-cam texture;
  stitch stays `tools/showcase.mjs` external-ffmpeg (frozen).
- Fixes: Look — in-engine video-texture playback for MP7 theater/kill-cam
  (post-fight replays on an arena screen, cutscene slates) without an
  encoder in the tree.
- Net lines: S (~90 lines mailbox + upload + drop-on-gone, reimplemented).
- Proof (proposed spike, not run): 30-packet H264 fixture (2 resolutions to
  force one resize) through mailbox-upload vs naive queue-every-frame;
  metric applied-vs-dropped counts + px-diff vs ffmpeg-reference decode +
  per-frame upload ms on RTX 3050 + llvmpipe parity + bytes x2.
  KILL if any queued-frame backlog grows unbounded (mailbox must drop) or
  px-diff vs reference >0.5% or any pass over its per-pass ms bar or parity
  drift >0.004 or any tick-byte drift (presentation only, tick untouched,
  golden `d57b5c8ae3096614` held).
- Effort/risk: S effort; risk is decode-cost smuggling (their thread hides
  openh264 CPU; ours must meter the EXTERNAL decode wall separately and
  never block the frame on it) and YUV-RGB-BGRA double convert (their TODO;
  keep until ms bar forces YUV-direct). Plan prefix: MP (MP7 leg, feeds
  MP15/SHOW1). Moves FOCUS Now pillar 1 look-live-on-GPU toward A4;
  EMPIRE proof-and-pull.
- Spike: fixture 30 H264 packets (2 resolutions) → mailbox texture;
  baseline naive queue-every-frame → candidate take-latest + resize-on-change;
  numbers: drops counted, px-diff ≤0.5%, ms on O5, digest x2.
  Kill: backlog growth OR px-diff >0.5% OR ms over bar OR any tick drift.
