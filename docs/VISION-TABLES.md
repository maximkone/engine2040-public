## Research contract

- Read this file, ROADMAP, the affected subsystem and LADDER before searching.
  Each research batch has distinct questions across competitor code, adjacent
  implementations and arXiv methods; use existing seats, no nested helpers.
- Compare at least three serious approaches per dossier, including the current
  implementation. Read source plus tests/issues; for a paper read method,
  limitations and available code. Capture repo revision/path, paper ID/version,
  license, evidence date and rejected alternatives. Search beyond the seed map.
- A candidate names an existing consumer, baseline, target, hardware/data,
  integration cost, failure case and proof command. Reuse mature foundations;
  build custom machinery only for a measured gap. No GPU gain from CPU-only proof.
- Research merge deduplicates into LADDER; one highest-value feasible spike per
  wave, alongside the blocking delivery work. After three research dispatches
  on one question: local experiment, dated rejection, or exact blocker with
  owner and recheck trigger. No unchanged re-research.
- Judge adoption independently. Keep only gains without golden, speed, visual
  or usability regressions. Retro counts sources tested, changes landed and
  finish bars moved, not papers collected. Extend the weakest uncovered vision
  part every five waves; retain all three games and the full engine ambition.
- Depth coverage and the next consumer milestones are in `plan/frontier.md`
  under "Full-layer research and delivery atlas". For any registered topic,
  derive up to four search angles from its atlas entry (hard problems, donors,
  gaps). Deep-read up to three sources and test the strongest approach; the
  entry is a menu, not a mandatory fetch list. `node tools/steal-next.mjs`
  names the stalest donor row plus the judged GitHub leads for the same part.
  Search code, tests, fixed issues, maintained forks,
  primary papers, failed reproductions, open prompts and adjacent domains.
- A future plan upgrade finishes with one outcome ready to dispatch and up to
  three dependency-held follow-ups. Reuse existing plan prefixes, reconcile
  current code with stale status, name the caller and first falsifying fixture.
  Only the lead promotes rows into `SPRINT.md`. A new plan needs a genuinely
  unowned capability, a VISION Plans entry and a README prefix entry.
- Tag each finding with `vision bar / layer / question`; merge the same question
  across compare, frontier and steal seats. A waiting accepted spike or an
  unwired feature takes priority over another survey on that question.
